# Cooperating Tauri verification

This adapter operates a host-registered, owned fixture through bounded IPC. It supports a numeric observation, registered semantic actions, cancellation, and an explicitly consented **private raw** PNG of the fixture's own window. Actions are cooperating application commands. They are not trusted OS mouse or keyboard events. No arbitrary app discovery, selectors, scripts, shell commands, URLs, window IDs, or caller-selected output paths are exposed.

Construct `CooperatingTauriAdapter` only after a trusted host launcher has registered the exact application/window, generated a fresh 32-byte nonce, and supplied its owned transport and new private artifact directory. Importing evidence or an artifact does not recreate that authority. Replies must match the complete identity and generation; unknown fields and malformed observations fail closed. A missing/denied/cancelled observation never becomes a passing comparison.

One operation is admitted at a time with a five-second deadline. Cancel advances the generation before signalling the transport; late replies cannot admit artifacts. Close is cached, fences pending work, and waits for the owned process's actual `close` event. TERM gets 2500 ms, then KILL gets 2500 ms; an unconfirmed exit retains private files and reports `cleanup-unconfirmed`. Signal delivery alone is not exit proof. The process transport drains/discards native stderr and nonprotocol stdout, without raw diagnostic tails.

Captures are limited to 8 MiB, 1920×1080, 16 files and 32 MiB total. New directories/files use 0700/0600; content hashes and file identities protect reads. Cleanup only removes matching owned files and retains replacements, symlinks and unrelated entries. PNG structural checks are admission checks, not sanitization. No private raw bytes are automatically published or labelled masked. The directory parent must be host-owned and canonical; the store does not defend against a malicious process running as the same OS user concurrently replacing ancestor directories.

The fixture source is in `tests/fixtures/tauri-verification`. Its Rust command manifest and capability restrict the command to the single local fixture window; verification authority is private stdin, not JavaScript-provided metadata. macOS capture obtains the live Tauri window's `NSWindow` and asks CoreGraphics for **that window only**. It never requests a whole-display capture or screen-recording permission. OS denial stays denied. Windows/Linux capture is unavailable. No platform is advertised as qualified until a real packaged fixture is built and exercised on that platform.

`bun --no-env-file tests/fixtures/tauri-verification/run-native.ts` is the real packaged entry point. It reports `BLOCKED` and exits 78 when the framework/packaged fixture is unavailable; it never installs a dependency or substitutes browser/standard-Rust results. The user approved an isolated private runtime pinned to Tauri 2.12.4, tauri-build 2.7.3, serde 1.0.229, serde_json 1.0.151 and Tauri CLI 2.12.3. The approved build used a separate private fixture with a resolved Cargo lock, verified crate checksums and pinned source/toolchain/package identity. `Cargo.toml.proposed` remains inactive: no active Cargo manifest or generated lockfile is committed. The checked-in runner still expects a package in its source fixture location, so that separate private build does not make the command universally available.

[PR #141](https://github.com/RunPhantom/Run-Phantom/pull/141) records the scoped macOS ARM64 qualification at `b08a1305ffe2efee2a14e6e47b001032798d00ca`: 19 actual SDK fixture controls and one packaged native journey with independently viewed, real owned-window pixels showing `0` then `1`. Actual consent denial, generation/cancellation fences and known-owned process closure passed. The earlier blank/stale-zero capture attempt remains preserved. Frontend readiness and exact render acknowledgement gate capture within the original four-second native and five-second adapter bounds; acknowledgement alone is not pixel proof.

Native stdin dispatch is serial, so a queued native cancel waits for the current dispatch to return. Response deadlines do not interrupt a native OS job already entered; cancellation of an in-progress OS capture is unqualified. Newly observed WebKit/XPC candidates disappeared, but their causal ownership remains **UNKNOWN** and was not inferred from process names. Central application daemon/worker/Team and shared product UI/registry integration remain pending. Windows/Linux capture is unavailable; full native platform, installed/copied/signed distribution and arbitrary native input remain unqualified. The native runner alone does not certify package freshness or all descendant-process absence; controlled host qualification must supply those witnesses.
